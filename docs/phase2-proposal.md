# Phase 2 提案書: PowerPoint 対応 + 提案書ドラフト生成

作成日: 2026-09-12
対象: 社内ナレッジ検索ボット（MVP 完了済み）の継続開発
関連: [計画書](plan.md) 10 章 Phase 2 ロードマップ / [MVP の完了報告](../README.md)

---

## 1. 要約

MVP では PDF / Word の社内文書 36 件を対象に、Slack から出典付きで検索・要約できることを確認しました（15 問テストで正答 15/15、部署別アクセス制御・監査ログ・取り消し手順も稼働中）。

Phase 2 では、次の 2 点を 10 営業日・初期費用 65 万円で追加します。

| 項目 | 内容 | 効果 |
|---|---|---|
| A. PowerPoint 対応 | 未取り込みの PowerPoint 500 件を、図中の文字も含めて検索対象にする | 過去提案書の大半を占める PowerPoint が検索できるようになる |
| B. 提案書ドラフト生成 | 「業界・課題・期間」を入力すると、過去案件 3 件を参照した新規提案書ドラフトを Word で出力 | 手作業だった「過去提案書を探して下書きする」工程を数分に短縮 |

月額費用は据え置きです（API 利用料が月数百円増える程度）。

## 2. 現状の課題

| 課題 | 現状 | 影響 |
|---|---|---|
| PowerPoint 500 件が未取り込み | MVP の取り込み対象は PDF / Word のみ | 提案書の多くは PowerPoint で作られており、検索しても出てこない |
| 図中の文字が取れない | 図表・スクリーンショットの中の数値や項目名は単純なテキスト抽出では拾えない | 提案書の肝である「効果の数値」「構成図」が検索にかからない |
| 新規提案書の下書きが手作業 | 担当者が過去提案書を探し、構成を真似て書き起こしている | 1 通あたり半日〜1 日。参照漏れ・古い数値の流用が起きやすい |

## 3. 提案内容

### A. PowerPoint 対応

```
PowerPoint（.pptx）
  → スライドごとにテキスト抽出（本文・表・ノート）
  → 図・画像は OCR（画像入力対応の LLM で文字起こし）してテキストに合流
  → 以降は MVP と同じ（見出し単位チャンク → Embedding → Supabase → RLS 付き検索）
```

- 出典は「ファイル名 + スライド番号」で表示します（PDF の「p.N」と同じ位置づけ）
- MVP の取り込みパイプラインはファイル種別ごとの抽出処理だけを差し替える設計になっているため、PowerPoint 用の抽出を 1 つ追加するだけで、チャンク分割・Embedding・権限制御・監査ログはそのまま使えます
- OCR は「画像を含むスライドだけ」に限定し、テキストだけのスライドには使いません（費用と時間の節約）
- 毎日 02:00 の自動取り込み、失敗リトライ、部署判定、機密区分の運用ルールはすべて PowerPoint にもそのまま適用されます

### B. 提案書ドラフト生成

```
Slack で /draft 業界=金融 課題=窓口業務の効率化 期間=6か月
  → 質問者の所属部署で見られる文書の中から、条件に近い過去案件を 3 件検索（MVP の検索をそのまま利用）
  → 3 件の構成・効果数値・スケジュールを根拠として、新規提案書ドラフトを生成
  → Word（.docx）に整形し、Slack の DM に添付して返す。参照した 3 件の出典も併記
```

- 入口は Slack のスラッシュコマンド（`/draft`）とします。既存のボット・認証・部署別アクセス制御をそのまま使えるため、新しい画面や ID 管理が不要です
- ドラフトの構成は「背景 / 課題 / 提案 / 効果 / スケジュール / 費用」の 6 節を標準とし、クライアント側の提案書テンプレートに合わせて調整します
- 参照した過去案件の数値は「出典付き」で入れ、出典の無い数値を書かないよう生成時に制約をかけます（MVP の「根拠が無ければ答えない」ルールと同じ方針）
- 生成したドラフトの内容は監査ログに記録し、誤アップロード取り消し時の対象にも含めます

## 4. MVP との関係（何を再利用し、何を足すか）

| 部品 | MVP | Phase 2 で足すもの |
|---|---|---|
| 文書取り込み | PDF / Word の抽出、見出しチャンク、差分取り込み、失敗リトライ | PowerPoint 抽出（テキスト + OCR） |
| 検索 | RLS 付きベクトル検索、閾値判定、出典生成 | 変更なし。ドラフト生成の「過去案件 3 件」検索に流用 |
| 生成 | 出典付き要約 | 提案書ドラフト用のプロンプトと Word 整形 |
| Slack | DM / メンションでの質問応答 | `/draft` コマンドとファイル添付 |
| ガバナンス | 監査ログ、機密区分、取り消し、月次レポート | ドラフト生成もログ対象に含める |
| データベース | `file_type` 列は既に `pptx` を想定済み | スキーマ変更なし |

新規に作るコードは「PowerPoint 抽出」「ドラフト生成」「Word 出力」「Slack コマンド」の 4 か所に限定され、MVP で検証済みの部分には手を入れません。

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| OCR の読み取り誤り（図中の数値を誤認） | OCR 結果には「図からの読み取り」と印を付け、回答時にその旨を表示。数値は元スライドの確認を促す |
| 古いレイアウトの PowerPoint（.ppt）が混在 | `.ppt` は取り込み対象外とし、失敗一覧に理由付きで記録。必要なら PowerPoint で `.pptx` に一括変換する手順を提供 |
| ドラフトが過去案件の数値をそのまま流用してしまう | 参照元を出典付きで明示し、「別案件の数値を新規案件の効果として書かない」制約をプロンプトに入れる。MVP で同じ問題を修正した実績あり |
| ドラフトの品質が担当者の期待に届かない | 9 日目に担当者評価を組み込み、テンプレートとプロンプトを調整。標準 6 節の構成はクライアントのテンプレートに合わせる |
| 他部署の提案書が参照元に混ざる | MVP の RLS をそのまま適用。参照元の検索は質問者の権限で実行される |
| ドラフトの外部流出 | Slack の DM にのみ返す。生成内容と参照元を監査ログに記録し、取り消し手順の対象に含める |

## 9. クライアントに決めていただくこと

1. PowerPoint 500 件の共有方法（MVP と同じフォルダ経由。SharePoint 直結は別提案）
2. 提案書テンプレート（Word）の提供と、ドラフトの標準構成（6 節案で良いか）
3. ドラフト生成を使える範囲（全員か、営業・戦略部門に限定するか）
4. OCR の対象（図・画像すべてか、表と数値が含まれるものに限定するか）。範囲が狭いほど初回費用と取り込み時間が減ります
5. 品質評価に参加する担当者 3 名
